# Aqua Paddle Product Modeling Plan

Date: 2026-06-15
Branch: `codex/pr-068-aqua-paddle-product-modeling-plan`
Status: Planning only. Do not publish Aqua yet.

## Summary

PR 066 and PR 067 confirmed that Aqua paddle data exists in the custom catalog as four draft/manual-review rows, but the current live TigerPingPong site models Aqua as one product page with required package options.

Recommendation: model Aqua as one public product page with required package options, backed by variants for the four sellable packages. Do not publish it yet. The current custom architecture has the right database primitives for this model, but the storefront and checkout code are only partially wired for variant/options. Publishing Aqua safely requires a small future code/data implementation, not just flipping the existing four draft rows active.

## Current Architecture Findings

The custom platform already has normalized product option and variant tables:

- `ProductOption`
- `ProductOptionValue`
- `ProductVariant`
- `ProductVariantOptionValue`
- `ProductVariant.priceCents`
- `ProductVariant.sku`
- variant-linked `ProductMedia`

The import path also supports variant rows in `data/import-review/tigerpingpong/v1/product_variants_import_v1.csv`, including up to two option pairs and `price_cents`.

The catalog API detail response already serializes variants and their option values in `apps/api/src/catalog/catalog.service.ts`. Public product detail pages can receive variant option metadata without a schema change.

The cart supports selected options:

- `CartItem.selectedOptions`
- `CartProductInput.selectedOptions`
- `getCartLineId(productSlug, selectedOptions)`

That means different option selections for the same product slug can remain separate cart lines.

The cart-to-checkout request also forwards selected options to the API, and order items already have `variantId`, `variantKey`, `sku`, `name`, and `unitPriceCents` snapshot fields.

## Current Option Support

One product with options is supported in the data model and partially supported in the UI.

The current storefront selector is generic enough to render any option group passed into `CheckoutButton`, but the only option groups currently generated by the product page are table colour options.

Current table behaviour:

- `apps/web/src/app/catalog/products/[slug]/page.tsx` builds checkout option groups only when `productKind` is `table`.
- It reads active variants and extracts a `Color` option.
- It presents this as required `Top colour`.
- `CheckoutButton` renders radio choices, blocks add-to-cart until the required option is selected, stores selected options in cart, and sends them to checkout.

Current accessory behaviour:

- Accessories, including paddles, currently get no checkout option groups.
- If an accessory had selected options in cart today, the API checkout service would reject them because non-table options are not supported there.

## Variant Pricing Support

Variant pricing exists in the database and import shape, but checkout does not currently use it.

Evidence:

- `ProductVariant.priceCents` exists in Prisma.
- The import script reads variant `price_cents`.
- The catalog API serializes variant `priceCents`.
- Existing ball variant rows include variant prices.

Current limitation:

- `apps/api/src/checkout/checkout.service.ts` calculates `unitPriceCents` from `product.priceCents`.
- It validates table variants only to identify a selected colour and SKU.
- It does not select `variant.priceCents` in checkout.
- It does not use variant price when creating order items or Stripe line items.

Conclusion: variant-specific prices are not checkout-safe yet. Aqua cannot use one product with four differently priced package options until checkout calculates the backend price from the matched variant when a variant price is present.

## Modeling Options

### A. One Product With Package Options

This best matches the live BigCommerce product page and is the recommended public model.

Benefits:

- One customer-facing Aqua page.
- One URL decision instead of four product URLs.
- Required package choice mirrors the live page.
- Cart line IDs can already separate package selections.
- Order snapshots can already store variant SKU and option-labelled names.

Current blockers:

- Accessory option groups are not generated by the product page.
- Checkout validation only supports table `Color`, not paddle `Package Options`.
- Checkout does not currently use variant-level prices.
- Existing Aqua rows are products, not variants under one parent product.

### B. Four Separate Products

This matches the current draft rows but not the live customer experience.

Benefits:

- Lowest code change if each row became active later.
- Checkout can already price each separate product from `Product.priceCents`.

Risks:

- Creates four storefront product pages where the live site has one.
- Forces premature URL/canonical/redirect decisions.
- Spreads shared copy and shared media across separate pages.
- Makes the customer choose from listing cards instead of a required package selector.

This should only be chosen if Shawn explicitly wants four public Aqua PDPs.

### C. One Parent Product With Variants Backed By Existing Draft Rows

This is the safest practical implementation path for the preferred one-page model.

Interpretation:

- Create or designate one Aqua parent product for the public PDP.
- Model the four current Aqua draft products as variant source records in the import/data workflow.
- Preserve the existing draft rows for traceability until the import shape is intentionally changed, then convert or supersede them through a focused data PR.

Recommended parent:

- Product key/slug should be approved before implementation.
- Candidate public slug: `aqua-outdoor-indoor-paddle` or `tiger-aqua-outdoor-indoor-paddle`.
- Do not decide redirects, canonicals, sitemap, robots, or DNS in this PR.

Recommended variants:

| Option label | Current draft slug | SKU | Known price |
| --- | --- | --- | ---: |
| `Single - Coral Red` | `tiger-aqua-single-coral` | `15891` | `$25.00 CAD` |
| `Single - Ocean Blue` | `tiger-aqua-single-ocean-blue` | `15890` | `$25.00 CAD` |
| `2-Pack w/ 3 Balls` | `tiger-aqua-outdoor-paddle-pack-2` | `15889` | `$45.00 CAD` |
| `4-Pack w/ 3 Balls` | `tiger-aqua-outdoor-paddle-pack-4` | `15888` | `$80.00 CAD` |

## Minimum Future Code/Data Changes

To safely publish Aqua as one public product with package options:

1. Add or convert one Aqua parent product in the import data.
   - Keep it draft/manual-review until media and checkout are verified.
   - Use the approved public slug and copy.
   - Set product price display deliberately. Because the page has a range, the current PDP may need a price-range display if parent `priceCents` alone is insufficient.
2. Add four Aqua variants under that parent.
   - Option name: `Package Options` or a shorter internal `Package`.
   - Values matching the live labels.
   - SKUs and exact known prices from the existing draft rows.
3. Update the product detail option-group builder.
   - Support required non-table option groups for Aqua/package variants.
   - Avoid loosening eligibility globally.
   - Keep table colour behaviour intact.
4. Update checkout option validation.
   - Match selected options to one active checkoutable variant for non-table option products.
   - Reject missing, extra, duplicate, or unknown options.
   - Keep all pricing authoritative on the backend.
5. Update checkout pricing.
   - Use matched `variant.priceCents` when a variant is selected and the variant has a valid price.
   - Continue using `product.priceCents` only for products without variant pricing.
   - Preserve Stripe Checkout, webhook-confirmed payment truth, order snapshots, idempotency, and safe errors.
6. Add reviewed Aqua media rows.
   - Product-level primary/gallery media first.
   - Variant-level media only after human review.
7. Keep the four current Aqua product rows unpublished or intentionally superseded.
   - Do not leave duplicate public sellable Aqua products active unless Shawn approves that model.

## Decision For PR 068

Do not publish Aqua in this PR.

Use the one-page-with-package-options model for future implementation if approved.
